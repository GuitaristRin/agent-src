> **本文件是研究记录，不是风格素材。** 任何 agent（Critic/echo/其他）不得读取本文件作为语体依据，不得借用、改写、拼接其中的任何句子。风格配方在《用户语体分析.md》，全部为解构后的构式与人工示例。
> 建立原因（v3.2）：亲示范本以 few-shot 进过一次 agent 上下文，当轮即被原句照抄（「比任何 lint 都干净」）。原文与 LLM 之间必须隔离。

## 一、评价档范本全文（作者亲示，kanesumi-element 评审，v3.1 收）

> 评价先给定位：这是一个把「设计语言」当成可审计对象来做的自绘 UI 栈，46 个控件和那棵元素树都是它的肉体，真正的骨头是 docs/CANON_VS_TEMPORARY.md 那张把「我们抄错了」和「我们有意不同」分开的表，加上 UWP_PRIMARY_SOURCES.md 里一串带 文件：行号 的一手取证。绝大多数做到这个体量的 Rust 界面项目只有一份 README 和一份 TODO；愿意把每一次偏离连同理由、连同推翻自己的那一次写进病历的，是少数。换个说法：这仓库像一间自己开的 ICU，每个数值都挂着监护仪，写错了先进病历，再决定是换药还是登记为「有意偏离」。这套「监护仪 + 病历」的组合，是它区别于同类项目的地方。
> 有两处判断力是硬的。第一处是把约定改成结构：UpdateCtx 干脆不提供 invalidate_measure（kanesumi-element/src/widget.rs:82），于是「动画只动视觉属性」不再是纪律而是能力缺失 —— 违规的代码根本写不出来。比任何 lint 都干净。第二处是迁移的接缝选得比大多数方案体面：paint 不重画，而是存下 self.state、灌入框架状态、转手调用旧 render、再恢复（kanesumi-controls/src/button.rs:127）。旧 API 因此没有变成第二套渲染实现，只是多了一套输入语义通路；ELEMENT_MIGRATION.md §1「只加不改」在这种设计下才站得住。scripts/verify.sh 也是被咬过的产物：clippy 命中缓存会让基线被静默写成空（它靠 bump lib.rs mtime 强编一次绕开，L100-108）、PowerShell 写出的 BOM/CRLF、glibc 排序与 Sort-Object 口径不一致、非 Linux 平台被 cfg 门控导致两端告警集不同（于是给基线行加了 @platform 标签）。最见品味的是 L47-64：找不到测试字体时判定为失败而不是放过，理由写得很清楚 —— 字体测试静默跳过等于没跑。
> 制度与现实脱节的地方也有，而且都是同一种病：规则写在纸上，没有一处由机器执行。AGENTS.md §1.5 要求「无新增告警」，而 verify.sh:76 只解析 clippy 摘要行里的「目标 → 告警数」，比的是数目不是身份 —— 删掉一条再加上一条，账面平了，脚本就绿。这是一枚装饰性的棘轮。旧测试模块里 if !font_available() { return; } 这种静默通过（button.rs:266）还留在每个控件的旧测试里，全局那层被脚本兜住了，逐个测试没有。外观验证则只有三张 PNG 手工 cmp（docs/PERF_BASELINE.md:48）—— 一个以「视觉语言」为立论的项目，把视觉回归放在测试之外，是把最要紧的那一格留给了人的眼睛。架构心脏 tree.rs 挤成 2300 行单体、末尾只挂了四行测试模块（真正的测试在 tests/tree.rs），对一份所有东西都依赖它的代码来说，这个形状迟早要付利息。
> 最深的一条保留意见在 Widget 的形状上：这个 trait 有 16 个方法，其中约8 个是策略开关 —— clips_children / scrolls_children / paint_overflow / has_visual_states / focus_visual / wants_realize / bring_into_view / accessibility。文档反复讲「保险机制由框架强制而非约定」，可这些开关本身就是一份约定清单：控件只要把 clips_children() 改回 false，或者把 paint_overflow() 填大，就合法地退出了保险。arrange_child 的槽位夹紧是真的硬，但硬在默认路径上，逃生舱和保险写在同一张表里。这不是原创缺陷（XAML 一样如此），可它意味着「结构上不可能飞出窗口」这句话只在默认值成立时为真 —— 而默认值靠纪律维持，不是靠类型。
> 至于那个更大的赌注：为保住 Ether 定制的 CPU 光栅与 dmabuf 直通而拒用现成框架。代价在 ELEMENT_TREE.md §Ⅱ 里写得诚实 —— 现成的无障碍、文本 shaping、十年份布局 bug 全部自己扛，E6 整期就是给 AccessKit 补一张票。这笔账只在 Ether 真是产品时划算；作为通用框架它没有市场，而 README.md 也没有这么宣称。知道自己在卖什么，是这类项目最容易犯而这里没犯的错。
> 总评：工程品味在同类项目之上，文档纪律近乎偏执，真正的短板不是代码而是约束的执行层 —— 棘轮是假的、视觉回归是手工的、进度的真源靠人记得更新。三样都是同一件事：把已经想明白的东西交给机器去守，而不是交给下一个会话的记性。

## 五、首评失败实录（v2 存档，防戏仿反面教材）

评审 Ether 仓库时产出：「一句话定性：」「换挡的中段」（stock 比喻）「把主体还掉了」（生造搭配）「代码是零行，零行」（平静处喷重复强调）；通篇加粗小标题+列表报告体；零意象零典故。判定：拙劣模仿。根因：语体主次颠倒 + tic 装饰化。

## 七、人工构式示范（v3.2 现造，v3.3 自 agent 语料撤出）

以下段落为示范构式现造（虚构对象：一个版本管理工具），演示 5.9–5.12 全部构式如何在一篇短评里咬合。原放在 user-voice 5.8 与 critic.md 语体底色；2026-10 按 Anthropic 分层研究结论（system 只装规则，示例属调用侧）撤出 agent 语料，仅供人工理解构式。

> 评价先给定位：这是一个把「快照」当成一等公民来做的同步引擎，冲突策略和合并队列都是它的器官，真正的脊柱是那份把「我们修坏过的」和「我们故意保留的」分开的清单，外加一串带 文件：行号 的复核记录。多数做到这个体量的工具只有一份更新日志和一处道歉区；肯把每一次数据事故连同当时误判的原因一并入账的，是少数。换个说法：这库像一间只雇一个园丁的温室，每一株都挂着名牌，长歪了先记档再修枝，而不是整盆扔掉重栽。它的克制是算过账的。
